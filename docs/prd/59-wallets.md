- Milestone and slice: `M3.9` (see [roadmap](README.md))
- Related: [53-payments.md](53-payments.md) (reference replay, proof, the sheet this one is modelled on), [56-money-accounts-and-categories.md](56-money-accounts-and-categories.md) (2200 and the Monnify account), [54-who-owes-and-statements.md](54-who-owes-and-statements.md), [72-portal.md](72-portal.md), [57-approvals.md](57-approvals.md) (the queue the requests join), [technical reference](../technical-reference.md) decisions D-385 to D-416, [ADR 0008](../adr/0008-append-only-balanced-journal.md)

## Summary

A family can pay money in ahead and spend it on its children's charges. Staff record the money a guardian hands over (**Record top-up**, with the receipt) and see every wallet; the guardian, through the API in this phase, pays charges from it and can set some aside for one child. A wallet is a view over journal lines on `2200 Student wallets`; no balance is stored. Online payments (EDU-305): each paying family has a Monnify bank account; what is transferred to it reaches the wallet by itself, confirmed with Monnify first. Guardians (EDU-306) see the wallet on their Fees page in the portal: the family's Monnify account, the balance, paying their children's charges from it, setting money aside, an opt-in auto-pay switch and the history with Trace. A mistaken top-up is cancelled, and money a family overpaid is paid back, by a request that a second person approves (EDU-307); both reverse with a new entry and never edit one. Credit a family paid ahead on a child's fee account before wallets existed is moved into the wallet once, after the owner reviews a report (EDU-308).

## Who uses it

| Persona                               | Permission(s)                                         | What they can do here                                                                                                                                      |
| ------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner                                 | all                                                   | See every wallet, record a top-up, connect Monnify in Settings > Online payments, review and move existing credit into the wallets                         |
| Bursar (Lekki or Ikeja)               | `wallet:read`, `wallet:topUp`, `wallet:requestRefund` | See and top up the wallets of families with a child on their campuses; create a family's Monnify account; ask for a refund or for a top-up to be cancelled |
| Principal                             | `wallet:read`, `wallet:approveRefund`                 | See wallets and the Requests tab; approve or decline the requests of others (not their own); no **Record top-up** button, the `POST` answers 403           |
| Administrator                         | `wallet:read`                                         | See wallets; no **Record top-up** button, the `POST` answers 403                                                                                           |
| Guardian                              | `wallet:readOwn`, `wallet:spend`                      | See their own wallet and history on the portal Fees page; pay their children's charges from it; set money aside and release it; switch auto-pay on or off  |
| Bursar, principal, administrator      | no `wallet:migrateCredit`                             | No **Move existing credit** button; the migration route redirects and both of its API routes answer 403                                                    |
| Student, teacher, member with no role | none                                                  | Not shown; the route redirects, the API answers 403                                                                                                        |
| Acting super admin, no reason         | read permissions                                      | Buttons hidden; every `POST` answers 403 `ActingReadOnly`, audited                                                                                         |

Scope: a staff member sees a wallet when the school matches and either they see every campus or any child linked to the wallet's guardian is on a campus they see. Anything else answers 404; a caller who can see it but lacks the permission answers 403 [tenancy-001]. A guardian reaches only their own wallet, found from the signed-in user, never from an id in the URL.

## Screens

### Wallets

- Route `/finance/wallets`, web-admin, Finance, after Payments, gate `wallet:read`, icon `wallet`. Search `q`, `page`.
- Header: title **Wallets** with an info tooltip, description "One wallet for each paying guardian. Open one to record a top-up." and, for `wallet:migrateCredit` only, an outline **Move existing credit** link to the migration screen.
- A summary line: "{n} wallets · ₦X held · ₦Y set aside · ₦Z free to use", over everything the caller can see, not only the page.
- One card with a search box (placeholder "Search guardian name or phone"), a count, the table and the numbered pager (10 a page).
- Table columns: **Family** (avatar, guardian name, phone), **Children** (count), **Balance**, **Set aside**, **Free to use**. Money always shows kobo, so an empty wallet reads **₦0.00**. Each row opens the wallet.
- States: loading (skeleton), error (`ErrorMessage`), empty "No wallets yet" ("A wallet appears when a guardian is set to pay a child's fees."), no match "No wallets match" ("Try another name or phone number.").
- Tabs **Wallets** and **Requests** (`?tab=requests`). The Requests tab carries a warning badge with the number waiting. It lists, newest first and 10 a page, every refund and top-up cancellation asked for on families the caller can see: **Request** (kind and "To {email}" or "Top-up {reference}"), **Family** (links to the wallet), **Amount**, **Reason** (with "Declined: {reason}" once declined), **Requested by**, **Status** (Waiting, Approved, Declined) and, while waiting, a **See in Approvals** link. Empty: "No requests yet".
- When money is held for requests the summary line adds "{₦H} held for requests" before the free figure; the free figure already leaves it out.
- The **Wallets** menu item shows the number of wallet requests the viewer can decide (`byNav.wallets`).

### Wallet

- Route `/finance/wallets/$walletId` (file `wallets_.$walletId.tsx`), gate `wallet:read`, search `page` (movements) and `topup=1` (the sheet is open). Breadcrumb Wallets › {guardian}.
- Header: guardian name, phone, **Request refund** (outline, `wallet:requestRefund`; hidden for an acting super admin without a reason) and **Record top-up** (primary, `wallet:topUp` only). Search `refund=1` opens the refund sheet.
- Three cards: **Balance**, **Set aside**, **Free to use**, and a fourth, **Held for requests**, while a refund or cancellation waits.
- **Monnify account** card (after the three balance cards): bank, account number and account name of the family's reserved account. With none: when the school has not connected Monnify, "Online payments aren't connected. An owner can connect Monnify in Settings > Online payments."; when it has, "This family has no account yet…" and, for `wallet:topUp`, **Create account** (outline). Toast "Monnify account created."; a refusal toasts the API's message.
- **Children** card: child (linked to their statement when on the caller's campuses), **Owes**, **Set aside**, **Can use** (the most that child's charges can take now).
- **Movements** card: date, movement ("Top-up from Uncle Bode · Cash", "Online top-up · Monnify", "Paid Ada Okeke's charges", "Refund paid out", "Top-up cancelled", "Credit moved from 2 children's accounts"), reference with a **Receipt** link for a staff top-up and a **Trace** link for an online one, who made it (blank for online), the **Cancel top-up** action and the signed amount; newest first, paged. A set-aside or release is listed beside them with the child, who made it, no actions and its signed amount marked "Balance unchanged" ([D-421](../technical-reference.md#decision-log)). **Cancel top-up** (ghost, `wallet:requestRefund`) sits on a staff top-up that has no cancellation; once one waits the row says "Cancellation waiting", once approved "Cancelled". A Monnify credit, a spend and a refund never offer it.
- **Trace** (dialog on an online movement): Monnify reference, payment reference, signature check ("Valid"), confirmation ("Checked with Monnify on …"), paid on, paid by the family (gross), Monnify fee, credited to the wallet (net) and the journal entry reference.
- States: loading, error, not found ("No wallet here", back to Wallets).

### Guardian Fees (web-portal)

There is no separate Wallet page. A guardian holding `wallet:readOwn` sees, on `/fees` ([72-portal.md](72-portal.md#fees-m37)), top to bottom:

- **Wallet:** the three figures (**Balance**, **Free to use**, **Set aside**; an empty wallet reads **₦0.00**), a **Top up** dropdown and, for `wallet:spend`, **Pay from wallet**. **Top up** shows the family's Monnify bank, account number (with a **Copy** button) and account name; when the school has not connected Monnify it says online payments aren't switched on and to ask the office to record a top-up; when it has but the family has no account yet it says the account isn't ready. The **Auto-pay** switch (off by default) reads "When money reaches the wallet, pay your children's oldest charges first."; it toasts "Auto-pay is on." or "Auto-pay is off.".
- **Owing** tile: what the family owes across the children who owe (a child in credit is not set against another's debt), **₦0.00** and "Nothing owed" at zero.
- The selected child's **Charges** card (unpaid charges, **Set aside** and **Release** for `wallet:spend`), then the **Statement** with its Term select, as today.
- **History:** every movement, newest first, ten a page, signed amounts, and what she set aside or released for a child ("Set aside for Ada", marked "Balance unchanged"); an online top-up has **Trace** (the same facts as the staff dialog).
- A note: "Sent money to the wrong account? Email {school email} with the reference and we will look into a refund." Without a school email: "Contact the school with the reference …".

**Pay from wallet** (dialog): a table of the children, the one who has owed longest first, with **Owes**, **Can use** and an amount field. A child's **Can use** is the lesser of what they owe and their set-aside money plus the free money; lines are taken in order, so two never count the same free money. Zero shows **₦0.00**; an amount over the cap shows the API's limit message and holds **Review payment**. **Pay all I can** fills the oldest first. Set-aside money is used for that child first. **Review payment** opens a confirmation (each child and the total); **Pay now** posts with a reference made when the dialog opened, so a retry replays. A 422 toasts the API's limit.

**Set aside** and **Release** (dialogs): a child and an amount, held to the free money and to what is set aside for that child. Toast "₦X set aside for {child}." or "₦X released for {child}.".

### Request refund (sheet)

- Opened from **Request refund**. Title "Request a refund", description "Pay money back to {guardian} out of the family wallet. A second person approves it."
- Fields: **Amount to refund (₦)** (required, above zero, no more than the free money; the hint names it), **Paid out of** (the school's bank accounts from `GET /finance/wallets/refund-options`; never cash or the Monnify account), **Parent's email address** (required), **The parent's email, saved as a file** (required file: screenshot, photo or PDF; uploaded as `wallet_refund_request`), **Reason** (required) and **Our reference** (generated `WRQ-…`, editable; the same request entered twice is recorded once).
- **Request refund** opens a confirmation (family, amount, account, email), then posts. Toast "Refund of ₦X requested. A second person has to approve it." A replay warns "Reference … was already recorded. Nothing was requested twice." The wallets, requests, approvals and activity refresh.
- Validation: "Enter an amount above zero.", the over-the-free-money message ("That is more than is free to refund. You can refund up to ₦X."), "Enter the parent's email address.", "Attach the parent's email before asking for a refund.", "Say why the money is being paid back.".

### Cancel top-up (dialog)

- Opened from a movement. Title "Cancel this top-up?", the top-up's reference and amount, a note that the top-up stays on record and cancelling adds a new entry, and a required **Reason**. The reference (`WTQ-…`) is made when the dialog opens, so a retry replays. Toast "Cancellation of ₦X requested. A second person has to approve it."

### Approving a wallet request

Both kinds are rows in the Approvals queue and the bell ([57-approvals.md](57-approvals.md)): **Wallet refund** and **Cancel a top-up**, decided by `wallet:approveRefund`. Approving a refund asks for **Payout reference**, the bank's own reference for the transfer. Declining needs a reason.

### Record top-up (sheet)

- Opened from **Record top-up**. Title "Record a top-up", description "Money {guardian} has paid into the family wallet."
- Fields: **Amount received (₦)** (required, above zero), **Received on** (default today, not in the future), **Into** (accounts that take the chosen way of paying; never the Monnify account), **How they paid** (the ways Payment rules switch on), **Receipt or proof of payment** (required file: photo, screenshot, PDF; uploaded as `wallet_proof`), **Paid in by** (optional), **Our reference** (generated, editable; the same top-up entered twice is recorded once).
- **Record top-up** opens a confirmation (family, amount, account), then posts. Toast "₦X added to {guardian}'s wallet." A replay warns "Reference … was already recorded. Nothing was added twice." The wallets, money accounts, ledger and home figures refresh.
- Validation: "Enter an amount above zero.", "Add the receipt (a photo, screenshot or PDF) before recording.", "The proof must be a photo, a screenshot or a PDF.", "Enter a reference. …".

### Move existing credit

- Route `/finance/wallets/credit-migration` (file `wallets_.credit-migration.tsx`), web-admin, gate `wallet:migrateCredit`; reached from the **Move existing credit** link on the Wallets header. Breadcrumb Wallets › Move existing credit.
- Title "Move existing credit", description "Credit families paid ahead on a child's fee account moves to the family wallet. Debts and history stay as they are."
- A summary line "{n} families · {m} children · ₦X to move · ₦Y can't be moved" and the primary **Move credit** button (disabled when no family has credit to move).
- **Families to move** card: one row per family (guardian name and phone, number of children, total) that opens to its children: name with a **Left** or **Graduated** tag, admission number, campus and credit.
- **Can't be moved** card, only when there are such children: child, why ("No guardian pays fees for this child", "Already moved") and the credit that stays on their account.
- **Move credit** opens a confirmation naming the families, children and total, then posts the figures that were read. Toast "₦X moved into {n} family wallets."; a repeat that found nothing left warns "There was no credit left to move." The wallets, ledger, money accounts, statements, activity and home figures refresh.
- A 409 closes the confirmation, shows "The figures changed. Check them again." and the fresh report.
- States: loading (skeleton), error (`ErrorMessage`), empty "No credit to move".

## Business rules

1. **A wallet is journal lines.** Balance = credits minus debits on `2200` tagged with the family (`journal_line.family_id`, the guardian's id). Set aside = the sum of the family's `wallet_earmark` rows. Free to use = balance − set aside. Nothing is stored.
2. **One wallet per paying guardian**, created by a trigger the first time a `guardian_student` row has `pays_fees` ([D-387](../technical-reference.md#decision-log)). A family with no paying guardian has none; a top-up for a guardian who no longer pays for any child answers 400.
3. **Top-up.** Dr the chosen cash, bank or POS ledger account, Cr 2200 with the family, one balanced `wallet_topup` entry. The money account must be usable by the caller and not a gateway (400); a retired one answers 400, a missing one 404. The way of paying must be on in Payment rules and the date not in the future. The receipt must be the caller's own unused `wallet_proof` upload (404 if not found, 409 if already attached).
4. **Replay.** A top-up is applied once per school and reference. The same request again answers 200 `replayed: true`; the same reference with another body, from another family or against a journal reference another entry holds answers 409 ([D-390](../technical-reference.md#decision-log)).
5. **Spend.** One request with an amount per child. Each line is capped at the child's receivable balance and at that child's earmark plus the family's free money, lines taken in order. A line over its cap answers 422 with the most that child can use. Earmark money is used first ([D-388](../technical-reference.md#decision-log)).
6. **Spend postings.** One balanced `wallet_spend` entry: per child Dr 2200 (family, student) and Cr 1100 (student, current campus). The spend shows on each child's statement as "Paid from wallet" and counts as paid.
7. **Earmarks.** A set may not exceed free money, a release may not exceed that child's earmark (422 with the limit); each is idempotent by reference (200 `replayed: true`, 409 for another body). Earmarks post no journal entry ([D-389](../technical-reference.md#decision-log)).
8. **Concurrency.** The wallet row is locked for a spend, set or release, so simultaneous requests never use the same free money. A spend also locks its children's rows, after the wallet and in id order, so a payment, adjustment or void posting for a child at that moment finishes first and the spend is checked against what the child owes now ([D-422](../technical-reference.md#decision-log)).
9. **Guardian routes** resolve the guardian from `guardian.user_id`; no wallet answers 404; a child who is not linked to that guardian answers 404 ([D-391](../technical-reference.md#decision-log)).
10. **Append-only.** `wallet`, `wallet_topup`, `wallet_spend` and `wallet_earmark` refuse UPDATE and DELETE. A top-up is undone by a cancellation (rules 24 to 30), never by editing it.
11. **Movements add up.** The journal movements of a wallet always sum to its journal balance. Set-asides and releases are listed as `earmark` items among them and never count toward it ([D-421](../technical-reference.md#decision-log)).
12. **Activity.** A top-up writes `wallet.topped_up` on each campus the family has a child on; a spend writes `wallet.spent` per campus of the children it paid for.
13. **Whole-wallet visibility.** A wallet that is visible to a campus-scoped staff member (any linked child on their campuses) is shown whole: its Children card and movements include siblings on other campuses, flagged out of scope with no statement link ([D-392](../technical-reference.md#decision-log)).
14. **Online top-up.** The Monnify webhook posts one balanced `wallet_topup` entry: Dr `monnify_collections` (by system key) and Cr 2200 with the family, for Monnify's net settlement amount, with the Monnify transaction reference as the journal reference and `posted_by` null, plus a `gateway_topup` row holding gross, fee and net ([D-394](../technical-reference.md#decision-log), [D-395](../technical-reference.md#decision-log), [D-396](../technical-reference.md#decision-log)). A transaction is applied once per school; a repeat answers 200 and changes nothing.
15. **Trust.** The webhook is public. The school's own signature over the raw body is checked before anything else, the transaction is re-fetched from Monnify with that school's keys and only the re-fetched amounts are used, and the transaction's account must be one of the same school's reserved accounts. A notification signed by school A can never credit school B, and school A's secret on school B's URL fails the signature ([D-394](../technical-reference.md#decision-log)).
16. **Fee.** The family pays Monnify's fee, so the wallet gets the net amount; the fee is kept on the top-up row and no expense is posted. Confirm Monnify's fee mechanics on reserved accounts before relying on `settlementAmount` in production.
17. **Reserved account.** One per wallet, made on demand by `POST /finance/wallets/:walletId/reserved-account` (idempotent; 409 until the school has connected, 400 when no guardian pays, 503 when Monnify cannot be reached, 502 when it refuses) and, best effort after the commit, when a guardian is admitted or made a payer. The account reference is `EDV-W-<wallet id>`, so a retry reuses the account ([D-397](../technical-reference.md#decision-log)).
18. **Staff cannot type a Monnify reference.** A reference starting `MNFY-` or `MNFY|` answers 400 like the other system prefixes ([D-398](../technical-reference.md#decision-log)).
19. **Activity.** An online top-up writes `wallet.topped_up` on each campus the family has a child on, by the system actor `system:monnify`, with no secret-like data key.
20. **Auto-pay.** Off by default. A guardian turns it on or off with `PUT /portal/wallet/auto-pay`; each change is a row of an append-only log and the latest row counts; its reference is unique within the family, so another family's reference never clashes ([D-418](../technical-reference.md#decision-log)). When money lands in the wallet, by a staff top-up or an online one, and auto-pay is on, the family's free money pays the children's charges in the same transaction, the child with the oldest unpaid charge first, set-aside money first, never more than a child owes. It is an ordinary `wallet_spend` posted as the guardian who switched it on, with reference `AUTOPAY-<credit reference>` and activity `wallet.spent`. A replayed credit pays nothing twice. If the guardian who switched it on is no longer a member or no longer holds `wallet:spend`, it pays nothing ([D-417](../technical-reference.md#decision-log)). If paying fails the credit still stands ([D-400](../technical-reference.md#decision-log)).
21. **Guardian history.** `GET /portal/wallet/movements` lists the guardian's own movements without who recorded them, the receipt file or internal ids; no wallet answers 404 ([D-401](../technical-reference.md#decision-log)).
22. **Zero.** Every figure in a wallet or a pay table shows kobo, so zero reads ₦0.00 ([D-404](../technical-reference.md#decision-log)).
23. **Refund note.** The Fees page tells a family who sent money to the wrong account to email the school profile address with the reference ([D-402](../technical-reference.md#decision-log)); the school then asks for the refund itself (rules 24 to 30).

24. **Held money.** A waiting refund or cancellation holds its amount out of free money: free to use = balance − set aside − held, where held is the sum of the waiting `wallet_refund` amounts and of the amounts of the top-ups waiting to be cancelled. A spend, a set-aside, auto-pay and a new request all cap against that free money, under the wallet row lock. The balance itself moves only when the reversing entry posts; declining releases the hold ([D-405](../technical-reference.md#decision-log)).
25. **Refund request** (`wallet:requestRefund`). The amount may not exceed the free money (422 naming the most), the account must be one of the school's bank accounts (400 for cash, a gateway or a retired one, 404 for an unknown one), and the parent's email file must be the caller's own unused `wallet_refund_request` upload (404 if not found, 409 if already attached). The same reference with the same body replays (200 `replayed: true`), with another body answers 409 ([D-408](../technical-reference.md#decision-log)).
26. **Cancellation request** (`wallet:requestRefund`). Only a staff top-up can be cancelled: a Monnify credit answers 409, an unknown top-up 404. It is refused with 422 when less than the top-up's amount is free (the family has spent or set aside part of it), and with 409 while another cancellation of that top-up waits or is done; a declined one may be asked again ([D-409](../technical-reference.md#decision-log)).
27. **A second person decides** (`wallet:approveRefund`), always: there is no Approval-rules switch for these kinds ([D-406](../technical-reference.md#decision-log)). The requester's own request answers 409 `SelfApproval`, except for an owner ([D-378](../technical-reference.md#decision-log)). Approve and decline update `WHERE status = 'submitted'`; the loser answers 409 `AlreadyDecided`. Approving re-checks the free money under the lock and answers 422 if it is gone, leaving the request waiting for a decline. Declining needs a reason.
28. **Postings.** A refund posts one `wallet_refund` entry, Dr 2200 (the family) and Cr the money account's ledger account, under the reference `WRF-{request reference}`; the bank's payout reference is kept on the request and is unique per school. A cancellation posts one `wallet_topup_void` entry that mirrors the top-up's own lines, family tag included, under `WTC-{request reference}` with `reverses_entry_id` set; the original entry is never touched and can be reversed only once ([D-407](../technical-reference.md#decision-log)).
29. **Append-only.** `wallet_refund` and `wallet_topup_cancellation` change only while `submitted` and are never deleted (`approval_record_immutable`); every id on them is tied to the same school by a composite foreign key.
30. **Activity.** `wallet.refund_requested`, `wallet.refunded`, `wallet.refund_declined`, `wallet.topup_cancel_requested`, `wallet.topup_cancelled` and `wallet.topup_cancel_declined` are written on each campus the family has a child on.

31. **Eligible credit.** A student's credit is the minus of the sum of debit less credit on `1100` for that student, when positive. A debt is never touched ([D-414](../technical-reference.md#decision-log)).
32. **Mapping.** Credit goes to the student's earliest-linked paying guardian (oldest `guardian_student.created_at` with `pays_fees`, ties by the smaller guardian id) who has a wallet. Students who have left or graduated are included and flagged. A student with no paying guardian is listed as not moved (`no_paying_guardian`) and keeps their credit ([D-415](../technical-reference.md#decision-log)).
33. **Posting.** One balanced `wallet_credit_migration` entry per family under the reference `WMIG-<guardian id>`, dated today, memo "Credit moved to family wallet": for each child Dr `1100` (the student, their current campus), one Cr `2200` for the family total. The reference is applied at most once through `LedgerPoster.post`; a taken reference is a replay. `WMIG` is reserved, so a client cannot choose it ([D-414](../technical-reference.md#decision-log)).
34. **Totals unchanged.** Per student, what is owed is identical before and after; credit on `1100` plus the wallet balance is identical before and after. A figure that reads `1100` alone (the "credit" total on Who owes) drops by what moved, because that credit is now wallet balance, which the guardian sees as such.
35. **One time.** A family whose `WMIG-` entry exists is never swept again. Credit that appears later stays on the child and is listed as "Already moved" ([D-414](../technical-reference.md#decision-log)).
36. **Reviewed.** `GET` returns the report. `POST` carries `expectedFamilies` and `expectedTotalMinor` from the report the person read. Under a `FOR UPDATE` lock on each family's wallet row and on the rows of the children to move (so a void or an adjustment on a child waits) the server recomputes the plan; if it differs it posts nothing and answers 409 `CreditMigrationChanged` with the fresh report in the body's `report`. When nothing remains it answers 200 `replayed: true` with zeros, also when the figures the person read were zero. The whole run is one transaction ([D-416](../technical-reference.md#decision-log)).
37. **Who.** `wallet:migrateCredit` is granted to no starter role, so only the owner holds it. The report and the move are school-wide, because a family can span campuses, so both answer 403 to a member who does not hold every campus, even with the permission. Every query filters by the school; another school's students, guardians and wallets never appear. An acting super admin without a reason gets 403 on the report (a read permission it does not hold) and 403 `ActingReadOnly` on the `POST`.
38. **Statement and wallet.** A child's statement shows the entry as "Moved to family wallet" with the row status `moved` ("Moved to wallet"), which counts neither as paid nor as a charge; the wallet's movements show "Credit moved from {n} children's accounts" and still sum to the balance. `wallet.credit_migrated` is written once per family on each campus of the children moved.

Migration `20261024120000_monnify_gateway` (EDU-305): `gateway_connection` (one per school, encrypted keys and their masked tails, mode, contract code, last test result; `ON DELETE CASCADE` from `organization`), `wallet_reserved_account` (one per wallet, unique account reference, append-only) and `gateway_topup` (unique `(organization_id, reference)`, `gross = net + fee`, `net > 0`, `signature_verified` must be true, composite FKs to the wallet, reserved account and journal entry, append-only). `GATEWAY_ENCRYPTION_KEY` (32 bytes, base64) is the only new environment variable; the webhook URL given to Monnify is `{BETTER_AUTH_URL}/webhooks/monnify/{school id}`.

Migration `20261025090000_wallet_auto_pay` (EDU-306): `wallet_auto_pay_setting`, an append-only log (organization, guardian, `enabled`, a `reference` unique per school, `created_by`, `created_at`, an identity `sequence` that orders it), with a composite foreign key to `wallet` (`ON DELETE RESTRICT`) and the `wallet_append_only` trigger. The current value is the latest row; nothing is stored on `wallet`.

Migration `20261026090000_wallet_refunds_and_cancellations` (EDU-307): the `wallet_refund` and `wallet_topup_cancellation` journal kinds, `wallet_refund_request` in `file_object_kind_check`, `wallet_refund` (wallet, the bank account it leaves from, amount, the parent's email and its file, reason, the client reference and request hash, the payout reference set on approval, and the approval columns of `payment_void`) and `wallet_topup_cancellation` (the top-up, reason, client reference and request hash, the approval columns; one open or approved request per top-up). Both use `approval_record_immutable`, carry `organization_id` and tie every id to the school by composite foreign keys. There is no self-approval CHECK, because an owner may decide their own request ([D-378](../technical-reference.md#decision-log)).

Migration `20261027090000_wallet_credit_migration` (EDU-308): adds the `wallet_credit_migration` journal kind to `journal_entry_kind_check`. No new table: the journal entry, the activity row and the `WMIG-` reference are the record. Its `down` refuses to run once credit has been moved.

## Acceptance criteria

1. Given a bursar and a paying guardian, when she records a ₦50,000 cash top-up with a receipt, then one balanced entry debits the cash account and credits 2200 with the family, the wallet shows ₦50,000.00 balance and free to use, and the movement lists the receipt.
2. Given the same request sent again, when it posts, then the API answers 200 `replayed: true` and nothing more is posted; with another amount it answers 409.
3. Given a Lekki bursar and a family whose children are all at Ikeja, when she asks for the wallet, its movements or a top-up, then the API answers 404; for a family with a child at Lekki she sees the whole wallet.
4. Given a principal, when she opens a wallet, then there is no **Record top-up** button and the `POST` answers 403.
5. Given a guardian with ₦12,000 free and a child owing ₦20,000, when she spends ₦12,001, then the API answers 422 naming ₦12,000; for ₦12,000 it posts one balanced entry and the child owes ₦8,000.
6. Given the same guardian and a child of another family, when she spends for that child, then the API answers 404.
7. Given ₦25,000 free and two simultaneous spends of ₦20,000, when both run, then exactly one succeeds and the wallet is never negative.
8. Given ₦8,000 set aside for Ada, when the guardian pays ₦10,000 of Ada's charges, then the ₦8,000 is used first and the set-aside figure falls to ₦0.
9. Given a school with no wallet money, when an owner opens Wallets, then every figure reads ₦0.00.
10. Given a school, when the Money categories chart loads, then 2200 Student wallets is listed and Monnify collections rolls into Money accounts.
11. Given an owner with sandbox keys saved, when a ₦50,000 transfer to a family's Monnify account is signed by the school's secret and Monnify confirms ₦49,500 settled, then one balanced `wallet_topup` entry credits the family ₦49,500.00, the top-up row keeps ₦500.00 as the fee, and the movement shows a Trace.
12. Given the same notification delivered again, when it arrives, then the API answers 200 `replayed` and the wallet is unchanged.
13. Given a notification with a wrong or missing signature, or an amount that differs from what Monnify confirms, when it arrives, then the API answers 4xx and nothing is written.
14. Given a notification signed by school A that names school B's account, or school A's secret on school B's URL, when it arrives, then B's wallet is not credited.
15. Given a bursar and a connected school, when she presses **Create account** twice on a family, then Monnify is asked for one account and both answers show it.
16. Given a bursar, when she opens `/finance/gateway/monnify`, then the API answers 403; given an owner, no response ever contains a key.
17. Given a guardian with ₦50,000 free and two children owing, when she opens Fees, then she sees the wallet, the Owing tile with the family total, each child's charges and statement, her History and the refund note, and there is no Wallet page.
18. Given the same guardian, when she pays ₦15,000 for one child and ₦5,000 for the other from the dialog and confirms, then one balanced entry is posted, each child's statement shows "Paid from wallet", and the History lists it; sending the same request again posts nothing more.
19. Given ₦20,000 free and the oldest child owing ₦15,000, when she enters ₦20,000 for the second child as well, then the dialog shows that child's limit and holds the payment back.
20. Given auto-pay is off, when a bursar records a top-up, then no charge is paid; given she switches it on and a top-up or a Monnify payment arrives, then the oldest child's charges are paid in the same transaction by a `wallet_spend` named `AUTOPAY-…`, and the same top-up sent again pays nothing twice.
21. Given guardian A and guardian B in the same school, or in two schools, when A asks for her movements, then she sees none of B's.
22. Given a guardian without `wallet:spend`, when she asks to switch auto-pay on, then the API answers 403.
23. Given a school with an email on its profile, when a guardian reads the refund note, then it names that address; with none, it asks her to contact the school.
24. Given a wallet with no money, when the guardian opens Fees, then every figure and the Owing tile at zero read ₦0.00.
25. Given ₦50,000 free and a refund request for ₦40,000 from a bursar, when she opens the wallet, then the balance still reads ₦50,000.00, **Held for requests** reads ₦40,000.00, free to use ₦10,000.00, and nothing is posted.
26. Given that request, when she asks for ₦10,000.01 more, then the API answers 422 naming ₦10,000; and when the guardian tries to spend or set aside more than ₦10,000, the API answers 422 until the request is declined.
27. Given the same request approved by a principal with the bank's payout reference, then one balanced `wallet_refund` entry debits 2200 with the family and credits the bank account, the balance falls by ₦40,000, the held figure is ₦0.00 and the movement reads "Refund paid out".
28. Given a bursar who asked, when she approves her own request, then the API answers 409 `SelfApproval`; an owner who asked may approve their own.
29. Given two approvers pressing Approve together, when both run, then exactly one entry posts and the other answers 409 `AlreadyDecided`.
30. Given a staff top-up of ₦50,000 that the family has spent ₦5,000 of, when a bursar asks to cancel it, then the API answers 422 naming the ₦45,000 still free; given an untouched top-up, the request holds ₦50,000, and once approved a `wallet_topup_void` entry mirrors the original (family tag included), the original entry is unchanged and the balance falls to ₦0.00.
31. Given a Monnify credit, when a bursar asks to cancel it, then the API answers 409.
32. Given another school's owner, or a Lekki-only bursar and a family whose children are all at Ikeja, when they ask for a refund, a cancellation or a decision, then the API answers 404; given a member without `wallet:requestRefund`, 403; given an acting super admin without a reason, 403 `ActingReadOnly`.
33. Given the same refund request sent again, when it posts, then the API answers 200 `replayed: true` and holds once; with another amount it answers 409.
34. Given requests waiting, when a principal opens Approvals, then both kinds appear with Approve and Decline, the bell and the **Wallets** menu count them (not **Payments**), and approving a refund asks for the payout reference.
35. Given students in credit on their fee accounts, when the owner opens **Move existing credit**, then the report lists each family once with its children, their status and campus, the totals match `GET /finance/wallets/credit-migration`, and a child nobody pays for is under **Can't be moved**.
36. Given that report, when the owner presses **Move credit** and confirms, then one balanced `wallet_credit_migration` entry per family debits `1100` for each child and credits `2200` for the family, each wallet rises by the reported amount, each child's statement shows "Moved to family wallet", and the fees owed on Who owes are unchanged.
37. Given the migration was done, when it is run again, or two requests arrive together, then the API answers 200 `replayed: true` with zeros and nothing new is posted; the page reads "No credit to move".
38. Given the figures changed since the report was read, when the owner confirms, then the API answers 409 `CreditMigrationChanged` carrying the fresh report, nothing is posted, and the page shows that report.
39. Given a bursar, principal, administrator, student or guardian, or a member with no role, or a member holding `wallet:migrateCredit` for some campuses only, when they ask for the report or the move, then the API answers 403 and there is no **Move existing credit** button; another school's owner sees and moves only their own school.
40. Given a family that was moved, when a payment later leaves a child in credit, then that credit stays on the child and is listed as "Already moved", and a bursar can still record a payment at the school and a top-up for the family.
41. Given a guardian switched auto-pay on and then lost `wallet:spend` or her place in the school, when a top-up arrives, then the credit stands and no charge is paid.
