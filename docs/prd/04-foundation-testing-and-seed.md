## Summary

Every slice must be checkable on its own: a migration, an API, a screen and an isolation test against real Postgres. This spec fixes the shared test harness those checks run on, a dev seed that recreates the prototype's Greenfield College so the local stack looks like the prototype (same people, classes, fees, payments and store), the e2e personas that map onto the prototype's personas, and the isolation-test pattern every slice copies. It also lists what in today's harness breaks when sign-up is switched off and fixed roles go away.

## Who uses it

| Persona                        | Permission(s) | What they do here                                                                                                       |
| ------------------------------ | ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Slice author (agent or person) | none          | Writes unit and integration tests with the fixtures; extends the seed with the slice's tables; adds the isolation block |

| `eduvault-e2e` runner          | none          | Provisions run-scoped personas through the real API and drives the browser and `curl`                                   |

Scopes applied: the harness itself has none; the isolation pattern exercises the campus, class and student scopes of [02](02-foundation-permissions-and-scopes.md). Out-of-scope rows answer 404; in scope without the permission answers 403 [tenancy-001].

## Business rules

### Test harness (`apps/api/test`, `libs/testcontainers`)

1. One Postgres container (`postgres:17.6-alpine`, from `@eduvault/testcontainers`) serves the whole `api:test-integration` run; `global-setup.ts` runs the committed migrations with dbmate and exports `DATABASE_URL`. Each test file gets one Nest app; each test starts from `TRUNCATE "user", "organization", "verification" RESTART IDENTITY CASCADE`. `TRUNCATE … CASCADE` ignores `ON DELETE RESTRICT` and fires no row triggers, so the reset keeps working after [03](03-foundation-ledger-and-documents.md) makes money tables restrictive and append-only. A new table that does not reference `organization` or `user` must be added to the truncate list.
2. Unit tests (`nx run <project>:test`) never start Docker or the network [testing-001]. Tenancy, permission, money and trigger rules are proved only in `api:test-integration` against real Postgres [testing-002].
3. Today's fixtures and what replaces them:

4. Fixtures create data through the same code paths as production (Better Auth server API, Nest services, the HTTP API). A fixture may insert directly with SQL only where production uses a direct insert too (starter roles), and never into journal or stock tables.
5. Every integration spec is named `apps/api/test/<area>.integration.spec.ts`; each module's spec has a `describe('isolation')` block (rules 22–24).

### Dev seed (`apps/api/scripts/seed.ts`, `pnpm db:seed`)

6. The seed recreates the prototype's Greenfield College, two other schools for the platform console, and the prototype's personas. It replaces today's Greenfield Academy / Riverside School seed.
7. It is idempotent: a re-run does nothing if the seed's marker school exists, and every money or stock step uses the prototype's references (`OPEN-<student>`, `TRF-20260905-NGOZI`, …) so a half-finished run can be completed safely.
8. It grows with the slices: a slice that adds a table adds that table's Greenfield rows to the seed in the same PR. A slice is not done until `pnpm db:seed` on a fresh database shows its screen with prototype-like data.
9. Every seeded login uses the password `password123` and `mustChangePassword: false`, except Kemi Lawson, the "just added" persona, who is left with a temporary password to show the change-password step.
10. Emails use the reserved `.test` domain (`funmi@greenfield.test`, `ngozi.okeke@example.test`), never the prototype's real-looking domains (`greenfield.edu.ng`, `gmail.com`), so no seeded address can ever receive mail once an email provider is configured.
11. Dates: the prototype's "today" is 2026-10-07 and every seeded date is absolute. The seed shifts every date by the whole number of weeks between 2026-10-07 and the run day (rounded down), so seeded "today" is a Wednesday within the last six days, weekdays stay weekdays and the scenario stays true (current first term, Musa "not seen" for 16 days, Uche inactive, Bola left, the mid-term break ahead) ([D-047](../technical-reference.md#decision-log)). `SEED_TODAY=2026-10-07` reproduces the prototype exactly, for screenshots. Document numbers take the shifted year, so `ADJ-2026-0003` and `CNT-2026-0001` in the Screens table become `-2027-` on a seed run in 2027.
12. Records are created in date order, so document numbers rise with dates (the prototype numbers its store-sale receipts after later payments). Balances do not depend on the order.
13. `created_by`, `recorded_by`, `approved_by` follow the prototype's actors: Chika records Lekki money, Yemi Ikeja money, Tunde admits and archives students, Funmi decides leave.

### Isolation-test pattern (every slice)

22. Every new table and route ships a `describe('isolation')` block in its module's integration spec, built on one shared fixture, `twoSchools()`:
    - school A with campuses Lekki and Ikeja; school B with one campus;
    - in A: `owner`, `lekkiOnly` (holds the slice's read and write permissions, member of Lekki only, no `campus:readAll`), `noPermission` (member only), and for student-bound reads `teacher` (class-scoped);
    - in B: `ownerB`, plus one row of the slice's kind in B and one in each of A's campuses.
23. The block asserts, for every route the slice adds:

| #   | Case                                                                                 | Expect                                                                                                                   |
| --- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 1   | `ownerB` reads, updates or acts on A's row by id                                     | 404                                                                                                                      |
| 2   | A's lists, as `owner`, never contain B's rows; a `campusId` filter naming B's campus | rows absent; 404 "Campus not found"                                                                                      |
| 3   | `lekkiOnly` reads or writes the Ikeja row                                            | 404                                                                                                                      |
| 4   | `lekkiOnly` lists                                                                    | only Lekki rows, plus null-campus rows where [02](02-foundation-permissions-and-scopes.md) rule 19 says they are visible |
| 5   | `noPermission` on A's own Lekki row                                                  | 403                                                                                                                      |
| 6   | No session                                                                           | 401                                                                                                                      |
| 7   | Create in A referencing B's campus, student, account or item id                      | 404 (and the composite foreign key refuses it if the service check is bypassed)                                          |
| 8   | Class-scoped `teacher` reads a student outside their arms (student-bound slices)     | 404                                                                                                                      |
| 9   | Student or guardian on a `readOwn` route asks for another child's id (portal slices) | 404                                                                                                                      |
| 10  | Referenced money or stock create sent twice (money slices)                           | one row, one journal entry; second answers 200 `replayed: true`                                                          |
| 11  | Creator approves their own request (approval slices)                                 | 409                                                                                                                      |
| 12  | Acting super admin without reason writes (from M1.5)                                 | 403                                                                                                                      |

24. A slice's PR description lists which of the twelve cases apply and why any are skipped; a reviewer rejects a new table or route without its block.

## Acceptance criteria

1. Given a fresh database, when `pnpm db:seed` runs twice, then the second run prints "Already seeded; nothing to do." and changes nothing.
2. Given the seed after all slices, when the seed check runs, then every figure in rule 16 matches and every journal entry balances.
3. Given the seed run on 2027-01-15 without `SEED_TODAY`, then first term is current, Musa is "Not seen 2 wk", Uche is Inactive and the next holiday is the mid-term break, as on 2026-10-07 in the prototype.
4. Given `SEED_TODAY=2026-10-07`, then every seeded date equals the prototype's.
5. Given each persona in the Screens table, when they sign in with `password123`, then they land where the table says and see the listed counts.
6. Given `disableSignUp: true`, when `api:test-integration` runs, then no fixture calls `/api/auth/sign-up/email` and every spec passes.
7. Given a new module spec without a `describe('isolation')` block, when reviewed, then it is rejected; given the twelve-case table, each applicable case has a test.
8. Given the e2e provisioning on a stack at M1.3 (which includes M1.2), when it runs, then `owner`, `foreign`, `admin`, `bursar`, `bursar2`, `teacher`, `newhire` and `superadmin` are created over HTTP and none is blocked; `student` and `guardian` are blocked until M2.4 + M2.8 with that reason.
9. Given an e2e run that passed, then no seeded Greenfield row was written by it.
10. Given a test that resets the database, when money and stock tables exist with `RESTRICT` and append-only triggers, then the reset succeeds.
