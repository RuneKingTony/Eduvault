Use the code-review skill on this branch's changes since the merge-base with origin/main (committed or not; see Base below).
- Run the skill's two axes as its parallel sub-agents, never inline. Each sub-agent writes its own findings, the spec axis to {{D}}/review-spec.md and the standards axis to {{D}}/review-standards.md; verify.sh rejects a review without both.
- Before you call anything unverified or unrun, read {{D}}/implement.json: its "ran" entries are commands the implement worker really ran, and its "unrun_specs" are the ones it could not. Do not report a gap it already closed; re-run a check yourself only when the tree changed since.
- Spec axis: the spec is {{D}}/ticket.json (acceptance criteria and title), {{D}}/design.md and {{D}}/tasks.md. Never skip it: every acceptance criterion is met, or it is a finding and its text goes in "unmet_criteria".
- Standards axis: CLAUDE.md (gotchas, tenancy, comment hygiene) and CONTEXT.md. A new table or route without a tenant-isolation test, and any added comment the comment rule below doesn't allow, are findings. At most 3 code-smell findings, none above minor.
Write the findings to {{D}}/review.md, classifying each as blocker, major or minor. Its first line is exactly `Result: <b> blockers, <m> majors, <n> minors.`; then the headings `### Blockers`, `### Major` and `### Minor` (write `None` under an empty one), and one top-level line per finding, `- **<ID>. <title>**` with an ID like S1 or T1 (a code-smell finding is a minor with an ID), details indented below it. verify.sh compares that first line with the findings and with review.json, and rejects a mismatch.
Then write {{D}}/review.json last: {"result": "pass", "blockers": <int>, "majors": <int>, "unmet_criteria": ["<criterion text>", ...], "summary": "<=200 chars"}. Blockers, majors and unmet criteria are findings, not a failure: set "failure_reason" only if you couldn't complete the review.
